## 2. Domain primer (read before designing anything)

- **Xenium:** measures RNA in situ; each detected transcript has (x, y) in µm; ~5K-gene panel.
- **Segmentation** assigns transcripts to cells → a **cells × genes count matrix**
  (sparse, mostly zeros).
- **Every cell has two positions:** physical (x, y in µm, where it lives in the tissue)
  and similarity (2D UMAP, who it resembles). UMAP distance ≠ physical distance.
  **The product's core value is linking both spaces: select in one, highlight in the other.**
- **H&E:** the same section stained and photographed separately. Needs alignment:
  µm ÷ 0.2125 → morphology pixels → inverse of the 3×3 affine from the 10x alignment
  CSV → H&E pixels. Verify the transform direction empirically; do not trust it blind.
- **TMA:** one slide holding a grid of ~1 mm cores from different patients.
  Hierarchy: **section (slide/run) → core → cell**. A patient may have several cores.
  One Xenium run covers ~35 patients.
- **Clusters:** 23 annotated cell types/states in the lab data `[PDF]`.

### 4.3 Synthetic TMA and scale fixture (deterministic, seeded)

The dev dataset is whole tissue, not a TMA. Generate:

- **`synthetic-tma`:** cut non-overlapping 1 mm circular cores from the tissue; assign
  `core_id`, `section_id` (3 synthetic sections), `patient_id` (some patients with ≥ 2 cores).
- **`scale`:** ≥ 443K cells, ≥ 100 cores, 62 patients, 3 sections, 23 clusters. If the
  tissue yields fewer cores, replicate cores with new IDs and jittered positions; reach
  23 clusters by deterministic sub-clustering of 10x groups. Used for performance and
  UI-at-scale tests. **Always labeled "synthetic" in the UI.**
- Region area is ~86.8 mm² and a 1 mm core covers 0.785 mm², so expect a few dozen non-overlapping
  cores at most: plan on replication for `scale`.
- **`fixture`:** tiny subset (≤ 5 MB, CC BY attribution) committed for CI.

### 4.4 Canonical data contract (the adapter boundary)

`source adapter → canonical dataset (validated) → asset builder → static assets → web app`.
The web app only knows the static asset format. Swapping to lab data = one new adapter + config.

Minimum entities (Tech Spec finalizes types, units, validation):
- `cells`: cell_id, section_id, core_id, patient_id, x_um, y_um, umap_x, umap_y, cluster_id, n_transcripts
- `genes`: gene_id, symbol, panel
- `expression`: sparse cells × genes; raw counts + display-normalized values (method documented)
- `clusters`: cluster_id, label, color, display order
- `cores`: core_id, section_id, patient_id, center_um, radius_um, bbox, public clinical fields (allowlist, Q4)
- `sections`: section_id, H&E image ref, affine transform, pixel size
- `dataset`: name, license, citation, provenance, `synthetic` flag

Schema violations fail the pipeline loudly (pandera/pydantic or equivalent).

## 7. Out of scope for v1 (Won't) — with the cost that justifies it

- **Individual transcripts:** billions of points; breaks NFR-3 and NFR-5.
- **3D tissue reconstruction:** a Xenium section is ~5 µm thick, effectively 2D; high UX/render cost, no value for US-1..US-5. (3D UMAP stays Could, FR-U5.)
- **User-run analysis** (differential expression, re-clustering): breaks NFR-1.
- **Accounts, uploads of user data.**
- **HPC cluster as web server:** not its job; security and availability risk.
- **Plotein 2.0 deployment:** separate project.

## 8. Architecture: constraints and defaults

**Constraints (non-negotiable):** static-only, everything precomputed offline;
one-command pipeline; web app reads only the static asset format; data never in git.

**Defaults (deviate only via ADR with numbers):**
- Pipeline: Python ≥ 3.11 with `uv`; `spatialdata-io`, `anndata`, `scanpy`, `pandas`/`pyarrow`, `zarr`.
- Assets: typed binaries (`float32` coordinates, `uint8` cluster ids), per-gene expression
  chunks (quantized), JSON manifest with hashes; tiled image pyramid for H&E.
- Web: React + TypeScript (strict) + Vite + deck.gl (WebGL).

**Budget math to anchor design:**
- One 2D embedding: 443K × 2 × 4 B ≈ **3.5 MB** → UMAP alone nearly fills NFR-3. Plan the initial payload accordingly.
- One gene, dense `uint8`: 443K B ≈ **0.44 MB**; sparse is usually far smaller → per-gene files are compatible with NFR-4.
- 5K genes × ≤ 0.44 MB ≤ **2.2 GB** → fits NFR-13 with room for H&E pyramids.

**Required ADRs in Phase 0** (`docs/adr/NNNN-title.md`, ≤ 1 page: context, options with
trade-offs, decision, consequences, plus one line naming the system-design building block
involved, e.g. caching, tiling, CDN, object storage):
- 0001 Build vs adopt: custom deck.gl app vs existing open-source spatial single-cell viewers (e.g. Vitessce, Viv) as the whole app or as the rendering layer. Decide with the requirements above, especially FR-T1, FR-C3, FR-G6 and NFR-16.
- 0002 Static asset format (binary layout, chunking, compression, manifest).
- 0003 Expression storage and fetch strategy (NFR-4).
- 0004 H&E pyramid format and alignment approach.
- 0005 State management and versioned URL schema (FR-G6, NFR-16).
- 0006 Hosting requirements for LIIGH + public demo host (range requests, compression, cache, HTTPS).
- 0007 Testing and performance-measurement strategy.
- 0008 Public generic tool vs private study overlay: what may live in a public repo before the paper
  (Q10), and how study-specific text and config would move to a private overlay.

## 9. Engineering standards

- Monorepo: `pipeline/`, `web/`, `docs/`, `scripts/`, `fixtures/`, `.github/`.
- `make` targets: `setup`, `data`, `pipeline DATASET=…`, `dev`, `test`, `e2e`, `bench`, `verify` (lint + typecheck + unit + e2e + bench + budgets), `build`.
- Python: ruff, mypy strict on `pipeline/`, pytest. Web: TS strict, eslint, prettier, vitest, Playwright, axe-core, Lighthouse CI.
- CI (GitHub Actions) runs `verify` on `fixture`; full-scale budgets run locally and are recorded in `docs/perf.md`.
- Pre-commit: block files > 5 MB and data extensions (`.h5ad .rds .h5 .parquet .zarr .tif .tiff .ome.tif`) outside `fixtures/`.
- Conventional commits; one branch per phase.
- Limited internal disk: deployment tests use a local nginx (e.g. Homebrew), not a Docker VM. If
  `$DATA_ROOT` is on a spinning disk, `make bench` does one warm-up pass and `docs/perf.md` records the disk type.
- Repo docs: README (what, quickstart, pipeline, deploy, cite), CITATION.cff, CONTRIBUTING, LICENSE (pending Q9).

## 12. Working agreement for the agent

1. Never commit, upload, log or screenshot lab data (§4.1).
2. Never push to a remote, deploy, or contact anyone. The maintainer pushes and deploys.
3. Don't invent biology: labels, clinical fields and cluster names come from data or stay generic.
4. Measure before optimizing; report numbers against the budgets.
5. If a budget can't be met, propose a scope trade-off in `PROGRESS.md` → "Decisions needed". Don't silently lower a threshold.
6. Blocked on the lab → implement behind config with the default assumption, log it, continue.
7. End every turn by updating `PROGRESS.md` and printing the relevant verification output.
8. Every capability you finish adds a short entry to `docs/learn/`: what it does, why this design, how to verify it by hand.
9. All data paths come from `$DATA_ROOT` (dev) and `$LAB_DATA_DIR` (lab, encrypted volume). Never write data into the repo.
